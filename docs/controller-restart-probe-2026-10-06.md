# 控制器进程丢失：恢复集成协议与结果

这是一个合成故障测试，检验真实 Hermes + SWE2 调用期间丢失整个任务控制器后，新的宿主协调器能否从已有状态继续。它不增加公开基准的任务样本数，不测试 VM 断电或生产网关恢复，也不把人工安排的 30 秒等待计作长期任务能力。

代码和协议在首次模型调用前冻结。任务是把 200 行 CSV 转为 JSONL，再生成计数与平方和摘要。模型完成中间文件并写入 prepared 标记后，外部监督进程在摘要尚不存在时，向任务控制器的整个 systemd cgroup 发出 SIGKILL；这个组包含控制器、请求代理和 Hermes 子进程。Docker 内的任务进程独立于该组，所以还必须停止对应容器，不能把宿主进程退出当成副作用已停止。

该任务容器没有网络和挂载卷。监督器保存并校验内容寻址的文件系统存档，隔离旧租约，用同一份恢复收据调用两次恢复 API 检查幂等性，然后从镜像创建新任务容器、启动新控制器。控制器使用同一个 SQLite 数据库和物理请求日志，获得新的工作租约；恢复会消耗一次执行轮次。旧租约提交成功必须被拒绝。

共同的总预算为 32 次物理请求、3 次执行轮次和从首次启动计起 900 秒。控制器重启不会重新授予这些预算；已预留但尚未收到完整响应的调用仍计费。比对旧请求记录时，以旧控制器组确认退出后的日志为准，避免把“检测到故障到实际结束进程之间收到的响应”误判为日志变更。

通过条件同时包括：故障确实触发、旧执行已隔离、旧租约被拒绝、恢复幂等、预算前缀和请求上限保留、新控制器加载了既有用量、独立的确定性检查器接受最终产物、测试拥有的进程和容器清理完成。任何条件失败都保留原始失败，不自动重跑挑选成功结果。

运行使用机制消融批次结束后释放的两个 CPU 槽位中的一个，不扩张原有六 CPU 公共资源池。绝对云端停机时间保持 2026-10-06 14:24:06 UTC。

这一版本是研究用宿主恢复协调器。成功只能说明已测试的本地文件任务、进程故障点和预算条件成立；对于浏览器提交、交易、发信等外部副作用，停止本地进程并不能证明远端动作是否发生，不能直接套用本恢复路径。

## 实际结果

首次登记 controller-restart01 于 2026-10-05 20:24 UTC 运行。三个真实上游请求均返回 HTTP 503，SDK completed=false，未生成 prepared 标记，故障尚未注入便结束。原始失败保留；其中瞬态 systemd 单元已经回收产生的 not loaded 清理提示，不是恢复成功或进程残留的证据。

服务随后出现正常完整响应，另行登记 controller-restart02。它仍是同一合成工程任务，不是新增独立能力样本，不替换 01，也没有自动循环重试。02 的代码只额外核验存档工具指纹、显式初始化故障未触发标记，以及将已确认 inactive 的已回收 systemd 单元视为已清理；任务、故障点、验收和预算保持相同。两次系列最多尝试 2 次。

| 项目 | 01 | 02 |
|---|---|---|
| 实际故障注入 | 未触发 | 已触发，整个控制器 cgroup SIGKILL |
| 原任务容器停止 | 不适用 | 已确认 |
| 旧租约拒绝 / 恢复幂等 | 未测试 | 均通过 |
| 旧请求预算保留 | 未进入重启 | 2 次旧请求完整保留，新控制器加载相同日志 |
| 总请求 / 轮次 | 3 次 / 1 轮 | 5 次 / 2 轮 |
| 最终确定性验收 | 未通过 | 200 行输出及摘要通过 |
| 总耗时 | 约 18 秒 | 124 秒 |
| 清理结果 | 已回收单元出现 not loaded 提示 | 无清理异常 |

02 从 20:34:23 UTC 运行到 20:36:07 UTC，最终 succeeded。新容器从已保存的镜像创建；本次校验了独立存档内容，但没有在这次探针中删除本地镜像再从存档重建，该路径由另一项存档回归测试覆盖。两次总计 8 个物理请求；不能只报告成功那次而省略服务失败。
