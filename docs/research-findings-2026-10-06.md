# 阶段性研究结论：验收、快照与长任务评估

本版结果证据截至 2026-10-06 09:21（北京时间）；24 任务扩展批次、跨阶段 2×2 消融与共同起点的六条补充对照均已完成，最终审计通过。多阶段迁移最终成绩使用 05:27:50 的完整快照，各批次采集时间见原始收据。这是本轮研究记录，结果尚不支持 Supergoal 已具备可靠的跨天自治能力。研究适配器、生产插件和独立评分器的结果分别记录。

`public-parallel24-v1` 的 120 个登记单元已全部有明确状态：22 个可执行任务 × 5 组，共 110 次模型试验；104 次正常评分、6 次执行异常，另外两个任务的 10 个单元因参考环境不可用而没有运行模型。下表按 22 个完整配对任务统计，包含已经审计的控制器失败与执行超时；环境不可用未填为模型零分。

完整 SG 对原生的任务配对为 3 个胜出、1 个落后，分差 +9.09 个百分点；精确 McNemar p=0.625，任务级 bootstrap 的 95% 差值区间为 −9.09 至 +27.27 个百分点。完整 SG 比原生多用约 56% 的请求；这个样本没有证明稳定收益。它比普通重发目标少通过两个任务，也比移除状态补充少通过一个。与移除审查的总通过数相同，但具体任务有 2 胜、2 负，不能据此断言审查没有任何作用。不同组的单次输出随机性、实际计算量及已披露的工具桥接缺陷仍限制因果解释。

SG 的 18 次在线 pass 中，extract-elf、model-extraction-relu-logits、query-optimize、video-processing 四个任务的官方结果为 0。另一个方向的错误也存在：install-windows-3.11 最终产物官方通过，但运行时仍以 fail 结束并耗尽六轮，使用 112 次请求。这里只能确认最终产物被错误拒绝，尚未逐轮评分，不能声称第一轮产物就已经正确。

只有 compile-compcert 与 install-windows-3.11 的完整 SG 实际进入多轮；前者同时出现求解超时和已审计的快照交接失败。普通重发目标额外通过的是 compile-compcert 与 large-scale-text-editing；前者受装置缺陷混杂，因此这两个胜出也不能都归因于简单重发架构。最后返回的 train-fasttext / sg_no_context 在一小时求解时限后由官方评分：模型大小通过、准确率 58.6% 低于 62%，保留超时与原始 0 分。

结束后复核了 30 个冻结源码文件、24 个官方任务文件树与初始镜像、110 个唯一控制器及请求记账，全部符合登记身份与 192 次调用上限。该复核不把已发生的失败变成通过。[完整逐单元结果及配对统计](public-parallel24-v1-progress.md)、[原始观测与最终审计](../experiments/results/research-evidence-20261006-073645/manifest.json)。

## 可复现的结构性故障

### 1. 独立审查仍可能给出错误的完成信号

对固定的评分前产物做了“执行器声明可见 / 隐藏”配对审查：计划 5 个产物、10 次审查，实际 4 个产物、8 次可执行；一个 ELF 产物的快照缺失，两个单元保留为不可用，没有替换样本。

错误 DNA 产物在两个条件下均被判为 pass。官方测试失败可对应到公开题面约束：实际完整退火区域超过上限，而审查者采用了错误的计数方式。隐藏完成声明没有修复这个错误。正确压缩产物在两个条件下都通过。正确服务产物则出现 fail/pass 分歧：审查对象只有文件系统，没有原服务进程，无法支持完整运行状态判断。

这否定了“仅屏蔽执行器声明即可解决验收问题”的修复假设。它说明自由文本证据和工具调用次数不等于完整、正确的验收覆盖。尚不能据此量化普遍误判率，或断言错误完全由同模型相关性引起。

修复方向是让验收记录明确绑定需求、被检查产物、观察范围及检查来源；运行状态缺失应成为可识别的不确定原因。模型编写的验证脚本仍需区分于经过校准的检查器。这里不向通用内核加入 DNA、交易等领域规则。

### 2. 快照超时会破坏评分交接

旧批次的四次 CompCert 任务均出现保存快照超时、暂停状态未恢复、官方评分无法执行。两次首要异常是 `RewardFileNotFoundError`，另两次先耗尽求解时间，随后又发生相同交接故障。对应 Docker 守护进程日志确认了评分阶段的 paused 拒绝。这些交接故障计入端到端失败，官方原始分数仍保留为空；时间耗尽与交接缺陷分别记录，可同时存在，不能相互替代。

实际容器故障注入已验证：旧的隐式暂停提交在客户端超时后留下暂停容器；显式管理暂停所有权的修复，在超时和取消两条路径均恢复原状态，随后验证命令可以执行。迟到的镜像不会被自动当成成功检查点。

另一次单独登记的真实 Hermes + SWE2 CompCert 回归已经结束：45 秒快照超时实际发生，容器恢复运行，官方测试完成并给出 **0 分**。求解在 2,400 秒耗尽时间，使用 31 次请求。交接回归通过，任务求解失败；这两个结论同时保留。该次不替代旧失败，也不增加能力评估的独立任务数。[原始回归记录](../experiments/results/research-evidence-20261006-0403/setup/checkpoint-handoff01-receipt.json)与[派生审计](../experiments/results/research-evidence-20261006-0403/setup/checkpoint-handoff01-audit.json)。

### 3. 有快照 ID 不等于能够恢复

初次审计发现 88 份报告记录了镜像 ID，其中 33 个镜像已不可用。受控复现确认：Docker commit 继承 Compose 项目标签，`compose down --rmi local` 会删除属于该项目的检查点镜像，即使它另有自定义标签。

新候选清除临时 Compose 所有权标签，并使用独立内容寻址存档。实际测试完成了“正常 Compose 清理后镜像仍在 → 独立存档 → 删除镜像 → 恢复相同镜像 ID 与文件内容”。已有冻结批次使用旁路保留器补存仍存在的镜像；这是尽力保存，无法追溯恢复已经丢失的镜像。06:24 的收据有 156 个完成存档、1 个捕获中、1 个捕获失败；其中包含同一多阶段问题的不同检查点产物，并非 156 个独立任务或完整恢复成功。

另一次空间维护逐项核对存档清单、完整 blob SHA256、镜像标签和所有容器引用后，移除了 21 个无容器使用的检查点镜像缓存。没有删除存档 blob，也没有使用强制删除或全局 prune。维护前后观测空闲空间约为 64.53 → 80.05 GiB；其他运行任务同时使用磁盘，因此这不是独立测得的净释放量。之后 Docker 缓存不在、但独立存档为 durable 的产物不能再次统计为“检查点丢失”。[维护计划、逐项收据与源码](../experiments/results/research-evidence-20261006-0607/manifest.json)。

第二次维护已按同一校验条件完成 96 个旧缓存的移除，核对 815 个不同存档 blob，独立存档删除数与强制删除数均为零；当前上下文研究的缓存被排除在计划外。维护期间空闲空间观测约为 67.72 → 82.73 GiB，随后新试验继续占用磁盘，07:50 仍有约 74.95 GiB 空闲。数字受同时运行的任务影响，不能视作净释放量。[计划、镜像盘点与完成收据](../experiments/results/research-evidence-20261006-075040/manifest.json)。

存档只覆盖镜像/文件系统，不包含进程内存、挂载卷或 VM 磁盘整体备份。不得把这项测试表述为整机故障恢复已经完成。

### 4. 主机名不能作为任务容器身份

SCBench 的第一轮接入测试启用 Harbor 网络隔离。任务容器共享辅助容器的网络命名空间，`/etc/hostname` 返回了辅助容器标识；旧适配器因此在错误文件系统里执行命令，实际限额也显示为 0。原生探针用尽 16 次请求后失败，记录保留。这属于适配器接入故障，不计入公开任务模型能力样本。

新候选从固定版本 Harbor 的 Compose 主服务解析容器，并独立核对两条执行路径的挂载命名空间。使用显式容器句柄的 OneDay 入口也保留。修复后的真实两阶段测试，原生、SG、mini 三组均通过；前后阶段使用同一任务容器、独立子控制器、累计请求预算，旧隐藏评分文件已清除。正式 SCBench 批次已在冻结的新候选上启动。[接入测试记录](../experiments/results/scb-transfer01-launch/scb-multistep-smoke02.json)。

### 5. 模型服务失败需要独立记录，HTTP 成功不等于生成完整

20:20–20:30 UTC 的固定审计窗口内，4 个控制器共有 11 次上游 HTTP 503，涉及公开任务和首次控制器恢复探针。原代理把异常包装成 502，使 SDK 日志与真正上游状态不一致；另有任务收到未包含终止事件的 SSE 流。SCBench 原生 DAG 的三阶段均为 worker_incomplete，官方严格测试均为 0；前一阶段是响应流未完整结束，后两阶段含 HTTP 503。这是端到端失败，不能单独归因于求解能力或拿来证明另一个 harness 更强。

开发版代理已保留上游 HTTP 状态码，禁止将第二段 HTTP 错误响应写进已经打开的 SSE 流，并将正常 EOF 但无终止事件记为 MissingTerminalResponse。5 个代理测试通过，覆盖预算保留、503、截断流与有效完整响应。旧冻结批次没有热更新；修复统一进入随后新冻结的 harness-transfer01 四组，原失败、请求计数和分数没有改写。[服务故障审计](../experiments/results/research-evidence-20261006-0443/setup/model-service-incident01.json)。

追加零模型诊断对固定观测中的 179 个控制器、402 段 episode 核对了原报告散列与输出文件：387 段记录了完成标记，9 段被终止后没有结果文件，4 段有显式失败标记，2 段明确达到单轮调用上限。这里包含 mini 适配器归一化后的完成标记，不能把 387 理解为 387 个成功任务，也不能单凭缺少结果文件推断原因。两个 iteration_limit 均是上述 DNA 审查；四个显式失败是三段原生 DAG 与一次 sqlite-db-truncate / sg_no_review。原分数保持不变；缺失、失败、预算上限和语义未完成应分别诊断。分类检查同时要求调用计数与 SDK 原因一致，不从模型最终文本猜测。[源码、输入清单与结果散列](../experiments/results/episode-boundaries01-evidence/manifest.json)。

### 6. 整个控制器进程组丢失后的恢复已完成一次真实集成验证

第一次探针因连续 3 次上游 503 在故障注入前退出，保留为失败，不能记为恢复成功。服务恢复后另行预登记第二次工程尝试；同一合成任务不增加能力样本。第二次实际结束整个控制器 cgroup，停止旧任务容器，将文件系统存档，再用新容器、新控制器继续。旧租约提交被拒绝，两次相同恢复收据的确认保持幂等，之前 2 次请求仍占用预算，最终共 5 次请求、2 次执行轮次、124 秒完成确定性验收，进程和容器清理无异常。

这验证了本地文件任务的一个进程故障点。整机断电、生产网关、远端副作用恢复没有被这次测试覆盖。[完整协议与两次结果](controller-restart-probe-2026-10-06.md)。

### 7. 文件工具报告失败时，写入可能已经发生

在真实 Hermes 轨迹中发现反复出现空原因的 `Failed to write file`，随后模型使用终端写入。另行运行一个零模型调用、独立网络隔离容器探针：普通 stdin 写入返回 0；Hermes 原子写入返回 1，文件工具报告 `bytes_written=0` 和失败，但独立 Python 读回确认三个文件都已写入预定内容，容器清理正常。

后续零模型诊断已定位到我们的研究适配器：`HarborTaskEnvironment` 遗漏了固定版本 Hermes Docker 后端会调用的 `init_session()`。这使每条命令都走登录 shell，且无法保留跨命令的 export。实际镜像的退出脚本调用 `clear_console -q`，在原子写入启用 `set -e` 的条件下，将已经成功写入并执行到 `exit 0` 的命令变成退出码 1。这是已复现的适配器接入缺陷，不能写成上游 Hermes 本身存在同一缺陷。

开发版已补齐会话初始化。真实固定版本 Hermes + 隔离容器的前后对照通过：旧路径报错但读回内容存在、export 丢失；修复路径成功写入含中文、空格路径的 200,017 字节内容，独立 SHA256 一致，export 正确保留。同时，`set -e; false` 和向 `/proc` 写入仍正确失败，主机凭据和 Docker socket 不可见，容器清理成功。整个验证没有调用模型。

修复没有热补丁写入当时已经冻结的旧模型批次，也没有替换既有成绩；随后登记的上下文研究统一使用了修复后的适配器。不能据此断言每条历史写入错误都有同一原因；但这项共同接入缺陷会干扰旧批次中 Hermes 组与 mini 的质量和成本归因。现有实验支持具体实现条件下的描述性比较，不能称为排除工具适配器影响的纯 harness 因果比较。执行失败收据也不能自动当作“副作用未发生”的证据。

## 本轮架构判断

目前证据支持保留小型事务内核，并重做内核周围的执行与验收契约。领域工作流应作为任务提供的配置或扩展，不能变成通用运行时的隐含完成标准。早期阶段内干预常未进入第二轮；新增跨阶段与共同起点实验已经实际触发了历史/需求干预，结果仍不足以说明这些策略能可靠完成任务。继续扩大模型调用量或默认回放全部历史，缺少本轮证据支持。

| 边界 | 本轮证据 | 已采取的变更或仍待解决的问题 |
|---|---|---|
| 状态与派工 | 控制器丢失后，新进程恢复，旧租约不能提交，重复恢复不重置预算 | 保留事务、租约和幂等收据；外部副作用仍需核对，不能盲目重放 |
| 任务执行适配器 | 容器身份曾指向辅助容器；终端初始化遗漏导致虚假写入失败 | 已修复显式容器绑定与会话初始化，并完成实际环境回归 |
| 检查点 | 镜像被清理、保存超时遗留暂停状态均真实发生 | 已分离任务清理与持久存档，记录暂停所有权、保存结果和恢复范围 |
| 模型传输与预算 | HTTP 503、无终止事件的流影响多个任务 | 已记录真实传输终态；重试与所有角色共享持久请求预算 |
| 完成判定 | 多阶段任务新增要求全部失败时，仍得到在线 pass | 研究中的模型审查不能独自承担可靠完成判定；需求覆盖、旧功能回归、产物版本和观察范围应分别记账，尚未证明新的语义验收方案有效 |
| 资源调度 | 执行、审查、管理、评分均消耗时间，磁盘同时保留缓存与存档 | 分组报告全部物理调用和阶段用量；缓存维护以完整存档校验和无容器引用为条件 |

生产 v2 候选已有操作者配置的验收标准、版本化检查器、正反例校准和争议状态；公开研究入口使用的是另一条在线模型审查路径。两者不能混作同一套验收能力。操作者检查器的“覆盖声明”和有限校准样例也不证明自然语言目标的语义覆盖完整。后续验收迭代应从明确需求到具体证据的可审计对应入手，用独立保留任务检查错误接受与错误拒绝，不能把已看过的隐藏测试包装成通用规则。
