# Supergoal Principles

Supergoal supplies durable execution control for a user-defined task. The task determines what to produce and how success is assessed.

## User-defined acceptance

The user goal, additional criteria, and explicit task contract are authoritative. Runtime defaults and critic suggestions must not invent new requirements. A text answer, a code change, a research summary, and an operational task may need different forms of evidence.

The generic runtime must not choose a workflow from words such as `edge`, `strategy`, or `hypothesis`. Domain methods belong in the task instructions or a separately selected skill. They do not become global acceptance gates.

## Durable control

Keep logical run identity, state, event history, budgets, and pending continuations across turns, process restarts, and compression. Pause on user interruption, budget exhaustion, or a current blocker. Completion requires the requested outcome; continuing for longer is not itself progress.

## Evidence appropriate to the task

Record actual tool results with provenance and distinguish them from model claims. Explicit execution requirements cannot be satisfied by prose. A requested text deliverable does not require an unrelated artifact, external source, or experiment.

Evidence-type presence is a necessary check when explicitly requested, not proof that the entire goal is achieved. The completion evaluator must assess relevance, output quality, and all stated criteria.

## Advisory criticism

The critic can identify drift, repetition, and missing task-specific evidence, then suggest another approach. It cannot rewrite the task contract or assert evidence into existence. Replanning must address unmet user criteria without prescribing a domain workflow.

## Compatibility and history

Preserve old data for audit and migration while removing retired policy from active prompts and decisions. Test the actual host capabilities and the real runtime path. A plugin version or a healthy server endpoint alone does not prove end-to-end compatibility.

## Permissions

Respect the task's permission boundaries and the host's approval rules. Additional autonomy does not authorize new operations outside the user's scope.
