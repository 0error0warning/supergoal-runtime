# Supergoal 的价值与范围复审

2026-10-06。本文在本轮代码和研究归档提交后重新评估项目定位，是基于现有证据的设计判断。它没有启动下一轮实验、部署候选或宣称新的能力结果。数据与代码边界见[研究索引](research-index.md)。

**建议将项目收缩为 Hermes 上的有限任务运行插件：保留可恢复的进度、明确的预算与停止原因，让完成依据可以核对。通用长任务能力增强仍是待验证假设。**

## 原始需求仍然成立，原来的实现假设需要收缩

用户想要的是：给出一个有限目标，必要时跨会话、跨小时继续推进，完成后停止，遇到真实限制时明确交还控制。这个需求可以拆成三个问题：

| 问题 | 本轮得到的证据 | 对项目价值的含义 |
| --- | --- | --- |
| 能否持续保存和恢复工作？ | 有状态事务、租约、等待、预算与特定进程故障的工程检查 | 能形成边界明确的可靠性功能；实际适用环境仍需验证 |
| 继续执行能否做对更多任务？ | 最大公开对照为 SG 15/22、原生 13/22、重发目标 17/22；额外请求与实现缺陷限制归因 | 尚未证明复杂控制循环值得其成本，也未证明普遍无效 |
| 能否正确判断何时完成？ | 新需求未实现仍被接受；正确产物也曾被拒绝；配置检查器同样可能不完整 | 是关键的未解决问题，增加一个审查角色不能自动解决 |

早期合成任务里，原生 Hermes、原生 GoalManager 和 SG 都一次完成全部保留样例；这类任务没有表现出额外运行层的必要性。后来的多阶段任务暴露了缺陷，却仍没有完整通过的任务。仅凭任务运行更久、模型调用更多或日志更丰富，无法证明用户得到了更好的交付。

因此，当前足以保留的是一个有工程依据的候选和可复核的研究记录。把它描述为可靠跨天自治系统，会超过证据。

## 哪些成果直接接近用户价值

稳定的任务身份、用户打断优先、持久派工、等待后恢复、预算不因重启归零、旧执行器不能覆盖新状态，都对应具体损失：进度丢失、重复工作、停不下来或恢复后行为不明。这些问题值得处理，但仍要通过实际宿主入口证明用户能够受益。

需要同时核对修复发生在哪一层。容器身份错误、终端会话初始化遗漏以及部分快照交接故障属于本项目研究适配器的问题。修复它们提高了实验的可信度；这些修复不能全部算成生产 Hermes 用户获得的新能力。

运行时的差异化也需要继续检验。事务、租约和检查脚本本身不能证明必须维护一个独立的复杂引擎。它们只有在具体使用场景中，比原生能力加少量自动化更省心、更可控，才构成持续维护的理由。

本次推送也实际暴露了集成成本：核心测试和打包通过，但[最新上游兼容检查](https://github.com/0error0warning/supergoal-runtime/actions/runs/37430966315)在应用旧 Hermes 接口补丁时冲突。继续维护这个项目，需要把宿主升级与接口适配的成本纳入判断，不能只计算模型调用成本。

## 验收的难题不能转移给配置文件

给检查器加版本、散列、正反例与证据链接，可以明确某次判定发生了什么。它仍无法自动证明检查器覆盖了全部自然语言要求。

如果每项任务都要用户先写完完整的评分程序，产品的有效范围就会集中在验收能够明确描述的工程任务。编写契约、维护检查器、处理争议和最后人工复核的时间，都应计入使用成本。

对于开放研究、写作和需求含糊的工作，可以提供产物、覆盖说明与待确认项，再由用户验收。不能因为程序必须选择一个终态，就把模型的信心升级成确定完成。模型生成的自测脚本也需要核查其来源与覆盖，执行退出码为零只说明该脚本通过。

## 值得保留的最小范围

| 范围 | 建议 |
| --- | --- |
| Hermes 插件接入 | 继续复用宿主的模型、工具、会话与权限边界；明确兼容接口的维护成本 |
| 任务状态与控制 | 保留任务身份、持久工作项、预算、等待/唤醒、暂停/取消、租约与恢复核对 |
| 验收记录 | 逐条关联用户要求、产物版本、检查结果和观察范围；分别报告新增要求与旧功能回归 |
| 语义判断 | 保留可替换接口与 unknown/争议状态；模型审查策略继续作为实验项 |
| 研究工具 | 与运行时职责分开，保留失败案例、冻结源码和分析；基准运行器不成为日常使用的依赖 |

默认多角色审查、无条件重放全部历史、更大的状态看板和更多轮数，都需要单独证明收益。当前没有理由继续把它们堆成默认配置。现有 v1/v2 并存可用于兼容和回退，但不宜演变为长期平行维护两套产品语义；统一入口应等真实宿主验证和迁移方案具备后另行实施。

## 再投入之前，需要回答的实际问题

下一次投入适合围绕一类真实、经常发生的工作，例如需要等待输入、跨会话修改代码并验证回归的有限任务。先保留一个简洁基线：原生 Hermes 或原生目标管理，加显式恢复和相同的验收条件。

项目的去留应由以下结果决定：

- 人需要催促、找回上下文、处理恢复和纠正错误完成的次数是否减少；配置与维护花费也计入。
- 完整交付率、错误接受、错误拒绝及旧功能回归是否改善；部分测试均分单独报告。
- 全部模型请求、实际费用回执、等待与执行时间是否值得这部分收益；缺失用量不补零。
- 所声称的恢复、等待和跨上下文机制是否实际触发，并经过真实插件入口验证。

若简单基线能够提供同样的使用体验，合理结果是进一步缩小插件，复用宿主能力，或停止独立引擎的扩张。若只有明确契约的工程任务受益，就将产品范围限定在那里。只有观察到实际交付与人工负担的改善后，才有依据扩大任务类型。

现阶段建议冻结已归档候选，保留生产现状，暂停增加机制与扩大基准批次。研究记录已有保留价值；下一笔投入应验证具体使用价值，而不是为此前的开发投入寻找合理化解释。
