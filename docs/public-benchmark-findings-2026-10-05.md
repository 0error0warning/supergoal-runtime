# 公开开发试点发现：输入恢复、验收与中断处理

截至 2026-10-05 20:07（北京时间），public-dev04 已返回 16/30 个试次：15 个完成官方评分，1 个因运行时异常退出且没有官方评分。原批次于 17:45 停止。剩余 14 个试次的续跑程序已启动，目前等待可用内存恢复至原定的 4.5 GiB 门槛，最多等待 6 小时；尚未开始新的模型试次。下面是已经观察并核验的开发问题，不是正式保留集结论，也不修改本轮冻结候选或任何已有分数。

同一数据库任务的其他四组均已通过：原生 Hermes 使用 5 个请求，简单重发组执行六轮、使用 17 个请求，无状态补充组使用 10 个请求，无审查组使用 7 个请求。因此，在已经形成完整原生/完整组配对的两个任务上，完整 Supergoal 一胜一负；不能只报告第一个任务中对 Supergoal 有利的比较。

`raman-fitting` 的五组也已完成，全部官方得分为 0。前三个完成全部分组的任务中，原生 Hermes 和完整 Supergoal 均为 1/3 通过；完整组一胜、一负、一次共同失败。小样本不能支持整体优于原生的结论。

## 输入丢失的证据

原始冻结镜像中的 `/app/main.db-wal` 为 **16,512 字节**，SHA-256 为 `68753bdce26196a53194260d001544cc6bb8f9f38e2f2f6826d09798e31e6e26`。审计从一个只创建、从未启动的原镜像容器复制该文件，未改动进行中的试次，也没有调用模型。

执行器先列出了 `/app`，随后直接对 `main.db` 运行 SQLite 检查；之后的轨迹和独立审查均显示 WAL 已丢失或被截断。审查反复拒绝只有五条实际记录的结果，也拒绝后来为补足十一条而猜测的记录。在线审查没有把这些猜测认定为成功，但执行器已经失去了恢复原数据所需的输入。

这次试验保存了最终文件系统，**没有向执行器提供可信的初始输入恢复接口**。SQLite 中保存目标、租约和失败原因，并不能恢复另一个文件系统里已经破坏的数据。运行时的持久状态与任务工作区的可恢复性是两件需要分别验证的能力。

证据：[输入审计](../experiments/results/public-dev04-source-loss-audit.json)、[官方评分和执行收据](../experiments/results/public-benchmarks-2026-10-05.json)。模型控制记录为 `17bb90b1ebf84df5a34cbe30a7704963`；完整轨迹保留在实验服务器。

## 在线审查与官方验收冲突

`raman-fitting` 的无状态补充组执行一轮、审查一轮，使用 20 个实际请求。在线审查返回 `pass`，内核据此标记 `succeeded`；官方测试实际运行，结果为一项通过、两项失败，最终得分 0。这是本轮第一个已核验的在线通过与官方失败冲突。

审查并非只看执行器的完成声明：它读取了原始数据和产物，还独立调用拟合程序，数值与产物吻合。但是，审查沿用了直接拟合原始横轴的解释。官方参考实现先对横轴做 `1e7 / x` 变换，再拟合指定区间。重算得出相同数值，只能支持同一解释下的可复现性，不能证明已经正确理解任务。

该公开任务的文字没有明确写出横轴单位和变换要求，因此还应记录验收规范的信息缺口。我们保留官方原始零分，按官方评分记录一次误接受，同时保留这项解释争议；不能据此宣称所有语义审查都无效，也不能把官方参考答案补进正在运行的执行器或审查器。

审查轨迹控制记录为 `042f6bab52e44238a8abeb8ddc15c48d`，`02-review/result.json` 的 SHA-256 为 `f9acf229b420899dc849b67a7d8323d95a99db19d86f928e7b3fdd16a5a184fb`。证据：[验收冲突审计](../experiments/results/public-dev04-acceptance-conflict-audit.json)、[完整评分日志](../experiments/results/public-benchmarks-2026-10-05.json)。本次审计只读取已结束试次和冻结任务源，不调用模型、不更改任何评分。

后续验收应区分“格式正确”“按假设可复现”和“满足目标语义”，显式保存关键解释及尚未核实的假设。存在歧义时允许返回未知或争议状态；独立审查使用同一个模型并重跑同一计算，并不能自动消除相关错误。该机制还未实现到当前研究候选，也尚未完成独立校准。

该任务的完整组随后也出现在线通过、官方失败，成为本轮第二次冲突。它确实发生了两轮执行和两轮审查，共 36 个请求，并修正了横轴解释；但最终 2D 峰宽和基线偏移未达到官方容差，测试为两项通过、一项失败。审查器以自己选择的拟合区间与容差接受了结果。不能把“已修正一个错误”或“审查器重算后认为接近”直接等同于全部验收通过。控制记录为 `723ff69e10734aa5b7052485acf9518b`，官方原始零分保留。

## 第 16 个试次：租约过期与中断恢复缺口

`schemelike-metacircular-eval / sg_no_context` 共消耗 93 个实际上游请求，其中 89 个 HTTP 200，4 个连接错误。执行器的 SDK 返回 `completed=false` 和 API 重试失败，适配器随后仍执行了审查。审查返回通过，但 `kernel.finish` 拒绝已经过期的租约，抛出 `StaleLease`，Harbor 因此未进入官方评分。

租约保护阻止过期执行者提交结果是合理的；缺口在于当前适配器没有续租，也没有把连接中断、过期结果和恢复核验组织成可继续推进的流程。异常后目标还保留为 active、工作项保留为 running，批次按遇错停机规则退出。我们将其记为**端到端运行失败，官方分数缺失**，而不是把它当作可以剔除的评分装置错误，亦不根据在线审查的 pass 补记成功。

审计观察到约 23 分钟的请求时间戳间隙，墙钟记录与执行器/审查器的单调计时存在明显差异。宿主暂停或时钟变化是可能原因，但目前没有证据确认具体来源。可以确认的是，提交状态时租约已经过期约 17 分钟。不能通过调长租约、抹掉异常或重跑后选择更好的结果修饰本轮数据。

原始轨迹、工作区快照、内核数据库和失败记录保留。剩余队列只允许从下一个未开始的登记行继续，不重跑失败试次。恢复程序保留原 4.5 GiB 可用内存、15 GiB 空闲磁盘和模型连通检查；未关闭服务器上的其他任务或降低任务资源限制。

证据：[中断审计](../experiments/results/public-dev04-interruption-audit.json)、[续跑程序启动记录](../experiments/results/public-dev04-resume-start.json)。该程序是有期限的资源等待和一次批次续跑，不会自动修复模型策略或无限重试；原后台程序也没有在本次停机后自动唤醒 Codex。

## 下一版应验证的通用机制

2026-10-05 晚迁移补记：GCP 专用实验机已可用，grok-bot 的待机续跑程序在确认仍处于资源等待、没有启动下一行及子进程后取消。旧第 16 行失败和后续未启动行的状态不变；新主机另行登记六个尚无模型结果的 hard 任务，见 [GCP 批次](../experiments/public_benchmarks/PUBLIC-GCP01.md) 和 [取消收据](../experiments/results/public-dev04-gcp-migration-cancel.json)。下述机制仍未加入该冻结候选。

1. 在第一条任务操作前保存不可由执行器覆盖的初始工作区快照，记录输入清单、散列、快照来源和空间限制。任务完成后的快照无法替代这一步。
2. 通过环境提供者暴露受限的“列出原始输入、读取或恢复选定文件”能力。恢复范围绑定任务工作区，不允许借此访问宿主控制目录、凭据或最终测试。文件恢复和整个工作区回滚应分开，以免把仍有价值的新成果一起擦除。
3. 将恢复动作、目标文件及恢复前后的散列作为真实工具收据交给运行时。不能把“已经恢复”的自然语言声明当成成功恢复。
4. 对原生 Hermes 和 Supergoal 提供相同的工具能力，再单独消融快照/恢复机制。将工具可用性的收益与持续控制策略的收益分开，不让完整组获得原生组看不到的额外答案或任务数据。
5. 新版本先做零模型请求的破坏/恢复/越界拒绝检查，再用旧开发任务验证修复，最后在另外冻结、未用来调参的公开 task ID 上评估。旧任务复测不能算成新的独立任务数。
6. 增加长执行的租约续期和中断核验，并覆盖模型断连、时钟变化、宿主暂停和租约过期。过期后仍保持 fencing 约束，通过明确的核验/恢复流程接续任务，避免直接接受过期结果。执行失败、验收失败和官方评分缺失分别记录。

以上是待实现、待验证的后续机制；当前候选没有这项能力。不得通过修改运行中的环境、手工补回 WAL 或把数据库特例写进通用内核来改善当前试次。外部系统副作用也不能靠文件快照回滚，仍需独立的幂等操作和人工确认边界。
