# 同一起点的需求回放对照：context-prefix01

这是看过 context-handoff01 结果后制定的开发实验，不是保留测试集。前一轮四组在第一阶段的任务输入相同，两个干预尚未发生，但 DAG 的严格通过率已经从 42.42% 到 84.85% 不等。后续整条轨迹的差异因此混入了初始产物差异。新的对照固定起点，直接检验“外部保存的公开需求是否有助于接续交付”，不重复第一阶段求解，不增加随机种子或独立任务数。

## 对照与起点

仍使用 file_backup、database_migration、dag_execution 三个已观察过的问题。每个问题只运行两种条件，各一次：两组都清空对话历史，一组回放之前的全部公开需求，另一组只接收当前需求。独立在线审查器始终得到相同的完整公开需求，工作区在后续阶段连续保留。

起点选择规则固定为 **context-handoff01 登记顺序中该问题的第一个试次，在第一阶段官方评分前的已保存产物**，不按分数挑选。分别对应 carry_ledger / file_backup、carry_current / database_migration、fresh_ledger / dag_execution。这三个第一阶段原始严格通过率为 65.625%、100%、60.606%；它们只是来源说明，不是新实验成绩。

每对分支必须使用同一不可变镜像 ID、相同的初始 `/app` 文件清单、同一第一阶段公开要求及同一受保护的评分历史备份。初始产物可以有缺陷，这些缺陷在配对两侧相同。模型阶段仍隐藏已知的评分历史文件，再原样恢复给官方评分器。不得把第一阶段分数、失败测试、官方日志或参考解放入模型提示。

仅运行原任务的第二阶段及以后，保留原有阶段名称、公开指令、测试与参考解。唯一任务定义调整是初始镜像指向共同产物，以及移除第一阶段的执行条目。三个问题分别剩余 3、4、2 阶段，共 **6 条轨迹、18 个阶段评分**。原始 2×2 的分数全部保留，新结果不与它合并成一次随机实验。

两组都有相同的审查反馈通道，审查器可能向执行器指出遗漏的旧要求；“不回放”因此只指初始执行提示，不等于永远无法重新获知旧约束。两组也都可读保留的工作区。

## 预算与冻结

每个后续轨迹最多 384 个新的物理请求，每阶段最多 128 个、最多 6 轮执行，执行时限 1,800 秒；官方评分时限沿用原任务。输出上限 6,000 tokens/请求，输入 token 不设硬上限。已完成的共同前缀调用量单列，不把复用四处计为新调用，也不悄悄计入新后续预算。

继续使用真实 Hermes 0.21.3 和 SWE2，以及相同的内核、容器绑定、终端初始化、检查点与传输修复。主机最多并行 6 条轨迹，每条在共享池预留 1 CPU / 4 GiB；任务容器配置沿用原任务。启动前保留 60 GiB 空闲磁盘，GCP 的绝对停机时间仍为北京时间 2026-10-06 22:24:06。

正式试验前必须通过：共同起点和受保护评分历史的真实容器接入检查；实际 SDK 输入中的历史为空、需求回放开关正确；原参考解在三个后续任务上的检查。随后冻结源文件、起点镜像、公开需求、评分历史备份、任务文件树、模型参数和固定执行顺序。任何门槛失败均保留，不替换为成绩更好的起点。正式单元不自动重跑。

## 预定分析

按问题配对报告后续阶段的严格测试平均通过率、后续全部阶段是否严格通过、每阶段当前测试模块的通过情况、同名旧测试由通过变失败的数量、错误在线接受、实际调用/token/时间。第一次阶段转换也与共同前缀的原始测试记录比较，但这些测试记录只供实验结束后的独立分析。

测试模块编号用于区分当前与旧测试，不代表完备的语义需求映射。平均分高但当前模块全失败时，必须同时披露。未知成绩和用量不填零；服务异常、求解时限与评分装置异常分开记账。

主要对照是同一前缀下“回放减不回放”的问题级差值；只有三个开发问题，每格一次生成，仍不作总体显著性或稳定优越性宣称。如果回放没有一致改善，保留这个负结果。该试验消除了初始产物不一致这一混杂因素，不消除后续模型随机性，也不证明跨天自治。
