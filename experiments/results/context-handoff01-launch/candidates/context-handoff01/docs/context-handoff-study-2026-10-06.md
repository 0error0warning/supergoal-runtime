# 跨阶段上下文消融：context-handoff01

这是针对 mechanism01 中未触发历史清空的后续开发实验。协议先于本批模型结果；不替换此前批次，不把重复任务算作新的独立样本。机器空闲不是增开样本的理由，实际发生的状态交接才是本批测量目标。

## 假设与范围

[Harness Design 的实证研究](https://arxiv.org/abs/2609.20804)将上下文、计划和动作接口分开干预；[LongHorizon-Harness](https://arxiv.org/abs/2608.01964)使用外部状态与新执行上下文。这使我们需要区分“旧对话还在”与“公开任务契约被重新提供”的作用。[SoL-Pi](https://arxiv.org/abs/2609.20519)启发开发与冻结评估分离；本批只用于开发机制检验。

研究使用已经观察过的 file_backup、database_migration、dag_execution 三个 SCBench 问题，分别有 4、5、3 个阶段。四组各运行一次，共 12 条轨迹、48 个阶段评分。统计单位始终是 3 个问题。没有新增随机种子、最好一次筛选或失败自动重试。

| 组别 | 跨阶段传入上一执行器的实际消息 | 显式重放此前公开需求 |
|---|---|---|
| carry_ledger | 是 | 是 |
| carry_current | 是 | 否 |
| fresh_ledger | 否 | 是 |
| fresh_current | 否 | 否 |

第一阶段四组输入相同；后续阶段由上游提供新需求。工作区连续保留，所有组独立审查器都获得完整累计公开需求，以免上下文处理同时改变验收标准。每个阶段的实际历史条数、散列、传入提示散列、需求重放数量及审查契约散列均记录。历史缺失的 carry 行保留为干预未激活，不能冒充保留历史成功。

这里的 ledger 是逐字记录的公开需求，不是模型总结的事实记忆。实验检验跨检查点的上下文充分性，不证明自主拆解目标、单个阶段的持续续跑或进程故障后的语义记忆恢复。普通保留历史仍有完整旧提示，因此移除重放不等于移除所有旧需求信息。

## 共同实现与启动门槛

全部四组采用相同新候选：v2 事务内核、相同在线审查、明确容器身份、快照生命周期修复、传输终态记账及已验证的终端会话初始化修复。旧候选源码不热改，旧成绩不能充当此次随机对照。

SCBench 的代码质量历史文件在模型阶段暂存到受保护的主机控制目录，模型退出后恢复原始字节、权限和所有者，再运行官方评分器。不得直接删除这一历史，因为官方评分器要用它计算差值。每个边界记录备份及恢复散列；异常、未恢复或模型篡改保留为装置故障。这仅处理已识别的该文件，不声称穷尽所有信息旁路。

启动前用真实 Hermes/SWE2 执行四组、每组两阶段的独立集成任务，直接核对送入 SDK 的 history 与提示，验证干预实际生效，并让第二阶段评分器确认第一阶段历史字节被原样恢复。集成任务不算能力样本。正式登记需冻结源码、问题文件树、镜像、预算及该门槛收据；既有参考解检查只在任务树和初始镜像逐项相同时复用。

每问题最多 384 个物理请求、每阶段最多 128 个，包含审查和传输重试；每阶段执行时间上限 1,800 秒，与之前开发研究一致，短于上游 7,200 秒。所有角色输出上限 6,000 tokens/调用，输入 token 无硬上限。审查期间暂停执行器，各活动问题预留 1 CPU、4 GiB，与既有 6 CPU / 48 GiB 池共享，最多 6 条轨迹。只有剩余时间足以覆盖整个问题的执行及评分上限时才接收。磁盘保留至少 60 GiB，不改变 GCP 的绝对停机时间。

## 预定分析

主要报告每个问题全部阶段的严格测试平均通过率、全部阶段全过与否、实际总请求/token/时间、旧功能回归及在线错误接受。先核对两个干预的实际激活次数，再解释分数；中途失败仍属于所分配条件。

分别在重放/不重放下对比 carry 与 fresh，在 carry/fresh 下对比重放与不重放，并给出各问题的差值和 2×2 交互差值。仅有 3 个刻意选择的开发问题，不作总体显著性或稳定优越性宣称。历史输入更长是干预的一部分，实际成本必须同时报告。未知成绩不填零，求解时限失败、控制器故障、评分装置故障分列；追加的只读审计不能覆盖原始结果。
